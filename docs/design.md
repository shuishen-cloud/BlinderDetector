# 关键设计决策

这份文档记录**为什么这么做**，不是**做了什么**。接口字段看
[api-contract.md](api-contract.md)，目录结构看 [README](../README.md)。

答辩时最值得讲的是 D2、D3、D7 三条。

---

## D1　全系统只有两个数据结构

**决策：** `Frame`（输入）+ `Announcement`（输出），所有路由统一。

**理由：** 四层由不同的人写，接口越多越容易分叉。统一成一对信封之后，
四层的差异被压缩到 `source` 字段和 `detail` 的形状里，新增一层不需要
新增任何顶层类型。

**代价：** `detail` 是无类型 dict，丢了编译期检查。用 `contracts.py` 里的
构造函数（`vision_detail()` 等）和 `test_contracts.py` 的形状断言补回来。

---

## D2　感知与安全是两条解耦的流水线 ★

**决策：** 第一层走云端 VLM（1–3 秒），第二层走轻量检测（<200 ms），
两者内部完全独立，只在播报出口汇合。

**理由：** 云端 VLM 单次调用 1–3 秒 —— **对避障来说完全不可接受**。
一个 3 秒后才播出的「前方 2 米有台阶」，用户早就走过去了。所以安全预警
在架构上就不能和场景描述共用一条链路。

这是本项目最重要的架构主张。它决定了：

- 第二层永远不能调 VLM
- 两层的延迟预算、触发频率、去重策略全都不同
- 第二层将来下沉到端侧模型时，第一层契约不用动

**答辩要点：** 「为什么不能一个模型全干？」—— 因为延迟量级差 10 倍以上，
强行合并会让避障失效。

---

## D3　风险分级用悲观距离 ★

**决策：** 分级一律用 `distance - distance_sigma_m`，不用中位数估计。

**理由：** 单目深度估计误差 30–50%，而且**误差是不对称地有害的**：

| 系统说 | 实际 | 后果 |
| :--- | :--- | :--- |
| 2 米 | 0.8 米 | 用户按 2 米的预期迈步 → **撞上** |
| 0.8 米 | 2 米 | 用户多绕一步 → 只是啰嗦 |

高估距离会让人撞上去，低估只会让人多绕一步。所以取悲观下界。

**配套决策：** 对障碍物**不播距离数字**，只播粗档（「就在脚前 / 很近 /
几米外 / 远处」）。「前方 2.3 米」这种虚假精度会让用户建立错误的心理预期，
而一次夸张的精确比十次模糊更伤信任。

**例外：** 第三层的距离来自地图/GPS，误差量级完全不同，**可以播数字**
（「前方 300 米右转」）。

---

## D4　去重键必须含风险等级和距离档位

**决策：** `dedup_key = f"obstacle:{type}:{position}:{risk}:{距离档位}"`

**理由：** 如果去重键只用障碍物类型，下面这个序列会被当成「同一个台阶的
重复」全部吞掉：

```
台阶(info,   3.2m)  -> 播报
台阶(warning,1.8m)  -> 被去重丢弃
台阶(danger, 0.7m)  -> 被去重丢弃   ← 用户撞上去
```

**被吞掉的恰恰是最危险的那一条**，因为它是「同一个物体的重复」。
这是安全系统里最经典的「告警抑制吞掉真实告警」缺陷，违反直觉的地方在于：
最危险的那条看起来最像「重复」。

---

## D5　近距离预警用短句

**决策：** 播报文本按剩余时间窗自动降级 —— 先试完整句，说不完就用最短形式。

**理由：** 用户以 1.1 m/s 走，2 米外的台阶只有 **2.7 秒**窗口，而完整句子
「前方几米有向下的台阶，注意脚下」需要 **3.7 秒**才播得完（中文 TTS 约
250 ms/字）。**物理上就说不完。**

所以规则是：在窗口内挑一条播得完的文本。

```
完整版  「前方几米有向下的台阶，注意脚下」   15 字 = 3750ms
最短版  「台阶，注意脚下」                    7 字 = 1750ms
```

**相关规则：** `ttl_ms` 必须 ≥ 播报耗时。否则消息在播完之前就过期了，
用户听到半句被打断 —— 两句话都没听懂。

---

## D6　置信度门限：宁可少报，不可误报

**决策：** 障碍物置信度 < 0.5 直接不生成播报。

**理由：** 播报的价值取决于用户是否相信它，而**信任是消耗品**。每次误报
（报了 danger 但没事）都在消耗信任。当误报率高到某个点，用户会开始忽略
预警 —— **包括真的那一次**。这在安全工程里叫告警疲劳（alarm fatigue），
是安全系统失效的头号原因。

推论：`ObstacleType` 只放团队能实际验证的类别。无法验证的不要进契约 ——
一个只报 3 类但每报必准的系统，比报 12 类但一半是噪音的系统有价值得多。

---

## D7　跌倒 `suspected` 态永不自动外呼 ★

**决策：** 检测到冲击后先走二次确认，用户不响应才升级到 `confirmed`，
此时才通知家属。

**理由：** 真跌倒和「把手机扔到床上」「快速坐下」「跳一下」在加速度计上
几乎无法区分。误报会骚扰家属、消耗信任；漏报则危及生命。**用布尔值表达
这个状态意味着只有一个阈值旋钮，而这个旋钮往任何一边拧都是错的。**

两条配套规则：

1. **沉默 ≠ 安全。** 取消**必须**要求显式动作（语音「我没事」、按键、
   点击、摇一摇）。绝不能因为「没检测到后续运动」就自动取消 ——
   失去意识的人同样没有运动。
2. **取消不能依赖网络。** 用户说「我没事」时如果连接正好断了，取消仍然
   必须生效。所以端侧本地就能完成取消，服务端只是通知者；倒计时也是
   端本地自减，不靠服务端 tick 驱动。

**假阳性抑制：** 步行节律是硬否决（人在走路就不是跌倒）；充电中 + 屏幕亮
+ 长时间静止**只延长二次确认窗口**，不构成取消理由。

---

## D8　绝不自动拨 120

**决策：** 升级链是「家属 → 社区网格员 → 建议手动拨号」，没有自动拨号。

**理由：** 自动拨急救电话是法律责任最重的一环，误报的代价不只是骚扰 ——
是占用真实急救资源。当前实现只做到「通知链走完后建议用户或家属手动拨」，
是否启用自动拨号需要指导老师确认。

---

## D9　规则与编排分开

**决策：** `detectors/` 只回答「看到什么」，`rules/` 回答「怎么判断危险、
怎么说出来」，`layers/` 只做编排。

**理由：**

- 换检测模型（YOLOv8 → 端侧 ONNX → 真实深度估计）时，安全策略不用跟着变
- 规则层不依赖 Starlette，能脱离 HTTP 单独测试 —— 140 项测试里 92 项是这一层
- 安全关键逻辑（跌倒状态机、风险分级）可以被穷举测试

---

## D10　不用 FastAPI

**决策：** Starlette + 标准库 dataclass。

**理由：** 开发环境是 Termux / Android，平台标签 `android_24_arm64_v8a`
（bionic libc）。`pydantic-core` 在 PyPI 上只有 `manylinux`（glibc）和
`musllinux` 的 wheel，**没有一个能在 Android 上用**，pip 会退化成源码编译
Rust（需先装 ~1.5 GB 的 rust 工具链）。

实测 `starlette` / `anyio` / `h11` / `idna` / `pytest` 全是 `py3-none-any`
纯 Python wheel，零编译。

**代价：** 失去 FastAPI 的自动 OpenAPI。用 `scripts/export_contract.py`
从 dataclass 反向生成 `docs/api-contract.md` 补回来 —— 契约仍是单一真源。

**注意：** 装 uvicorn 时不要带 `[standard]`，会拉 httptools / uvloop 等 C 扩展。

---

## D11　播报出口：服务端只做闸门，播放交给端侧

**决策：** 四条流水线共用一个播报出口，但它**只做去重和废数据过滤**。
排序、打断、积压保护、到期不补播，全部由端侧负责。

**理由（两部分）：**

**一、端侧需要一个单一有序通道。** 让端去轮询四个 HTTP 接口既费电又无法
保证顺序。这由 WebSocket 保证。

**二、但服务端不该跟着模拟播放状态。** 喇叭在端侧，服务端观察不到
「当前正在播哪条、播到哪了」。初期版本在服务端维护「当前播报」+ 优先级
队列来模拟播放，连出两个**永久静默**的 bug，根因完全相同 ——
服务端在猜自己看不见的东西：

1. 服务端没有播放完成回调，没人调 `finish_current()`，当前播报一旦被占住
   就永不释放，队列涨到上限后每条新播报都被丢掉，且不会自愈；
2. `/v1/emergency/tick`（以及 `smoke.sh`）会传 `now_ms=9999999999999`
   来强行触发升级链。这个未来时刻被记成「当前播报的开始时间」后，之后
   所有真实时间戳都成了「过去」，当前播报永远退不了场 —— 同样永久静默。

**这两个 bug 不是实现失误，是这个设计必然的产物**，所以那套状态机被拆掉了。
端侧本来就该做这件事：`Announcement` 已带 `priority` / `interrupt` /
`ttl_ms`，而契约里 `ttl_ms` 的定义就是「**从端「收到」起算**」——
到期与否本来就该端侧算。

**代价：** 端侧（将来的 Android / 小程序）要自己实现播放队列与优先级抢占。
换了载体就要重写一遍，且安全关键逻辑分散在各端 —— 这是这个决策明码标价的
代价，换来的是一条不会静默的播报链路。
