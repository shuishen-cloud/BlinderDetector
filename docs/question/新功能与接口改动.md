| :--- | :--- | :--- | :--- | :--- | :--- |

| 1.2 真实检测模型 | **可能**（若端侧算） | 否 | **可能** `/v1/safety/grade` | — | ★★ **与零编译约束冲突** |
| 1.3 真实地图 API（✅ 已落地） | 否 | 否 | — | `router` | 无 |
| 1.4 真实短信/推送 | 否 | ★ **可能要加投递状态** | `GET /v1/emergency/events/{id}` | `notifier` | 无 |
| 服务端语音识别（✅ 已落地，见 `docs/api-contract.md` §4.3） | 否 | ★ **是** —— 这条**不返回** `Announcement` | `POST /v1/asr` | `asr` | 无（复用 VLM 那把 key） |
| 2.1 上传目录隐私泄露 | 否 | 否 | — | — | 无 |
| 2.2 响应信封全量 `sent` | 否 | 否 | — | — | 无（前端**已经**不读 `.length` 了，破坏面比原先估计的小）★ |

## 一、接真实外部服务

### 1.1 真实云端 VLM —— **不是「只填 `.env`」**　【✅ 已完成 2026-09-23】

**现状**：`app/core/providers/openai_compat.py` 已实现 DashScope / 智谱 / OpenAI
三个子类（都走 OpenAI 兼容协议），换厂商只改 `.env`。这部分是**现成的**。

**但实测发现三个缺口，不修就用不了**（三个都已修掉，修法与「为什么」留在下面
—— 它们是这套系统最容易重犯的一类错）：

**① prompt 只要一句话，导致去重粒度塌成 1 个 key（最严重）**

prompt 写的是「只输出那句话，不要解释」，返回的 detail 是
`vision_detail(text, scene_conf=0.8)` —— `objects` / `ocr_results` **永远是空列表**。
而场景分类（`rules/scene.py`）是靠 `objects` / `ocr` 推导 `scene_key` 的。实测：

```
前方有个红绿灯，现在是红灯  → scene_key=default → dedup=vision:scene:default
左侧一米左右有人经过        → scene_key=default → dedup=vision:scene:default
前方人行道畅通             → scene_key=default → dedup=vision:scene:default
```

**三种完全不同的场景，去重键一模一样。** 后果：第一层会反复播同一句，
**场景变了也不播**（在闸门看来全是「同一个 scene 的重复」）。
也就是说，`VLM_PROVIDER` 一改，第一层等于废掉。

> **已修**：prompt 换成结构化 JSON（`scene_description` + `scene_conf` +
> `objects[]` + `ocr_results[]`），`parse_reply()` 负责解析与容错（模型爱把 JSON
> 包在代码围栏里、爱先说一句「好的，这是结果」，坏 JSON 一律退化成纯文本，
> **至少还能播**）。另外 `_detail()` 会**弹出 `scene_key`** ——
> `scene.apply()` 只在它缺失时才去推导，不弹的话三个场景照样塌成一个键
> （`mock` provider 一直是这么做的）。**契约没动** —— `vision_detail()`
> 的形状本来就是为此设计的，`tests/test_vlm_provider.py` 有两条用例专门钉
> 「不同场景必须拿到不同去重键」和「纯文本回包会塌成一个键」。

**② `scene_conf` 硬编码 0.8**

真实 VLM 的置信度没被提取出来，于是 `phrasing.hedge()`（低置信度对冲措辞）
**永远不会触发**。

> **已修**：`scene_conf` 从模型回包里取，钳到 0–1；取不到 / 不是数字才回落 0.8。

**③ 网络错误会变成 500，而且没有任何降级通告**

`describe_frame()` 里没有 `try/except`，`r.raise_for_status()` 一抛就冒到路由 →
客户端拿到 **500**，且**一条播报都不发**。

更麻烦的是：**`app/api/routes.py` 里定义了这个降级通告（`make_degraded_announcer()`
返回的 `announce_degraded()`），但全项目没有任何地方调用它**
（只有 `app.state.broadcast_degraded = ...` 这行赋值）。
所以 design.md 反复强调的「沉默不能有歧义」**在运行时失效这条路径上没有实现**。

> **已修（两处都修了）**：
> - provider 侧新增 `VLMUnavailable`，`raise_for_status()` / 网络异常 / 回包结构
>   异常全部转成它（401 查 key、429 限流、5xx 换时段重试都写在异常消息里）；
> - `Envelope.respond()` 捕获**任何**层异常 → 推一条 `source=system` 的降级播报，
>   并让接口**回 200**（回 500 等于「一条播报都没有」，而用户听到的安静会被
>   理解成「环境安全」—— 这是这套系统最危险的失效模式）。`main.py` 把
>   `make_degraded_announcer(hub)` 作为 `on_degraded` 传进 `Envelope`，
>   `app.state.broadcast_degraded` 仍保留。
>   `tests/test_api.py` 两条用例钉住「层失败不 500 + 一定出声」。
>
> 这是「接真实服务」的**前置条件** —— 真实服务一定会失败。

### 1.2 真实障碍物检测模型 —— 有个架构级冲突

**现状**：`detect(frame) -> list[dict]`，返回**未分级、未措辞**的原始结果，
分级/措辞在 `rules/risk.py` + `phrasing.py`。这个分工很好，换模型不动安全策略。

**冲突：真实检测库几乎都是 C 扩展，与项目的零编译约束冲突。** 实测 wheel 标签：

| 包 | wheel | 能否在 Termux 上装 |
| :--- | :--- | :--- |
| `onnxruntime` | `cp313-cp313-manylinux_2_28_x86_64` | ❌ C 扩展，android/aarch64 无 wheel |
| `opencv-python-headless` | `cp37-abi3-manylinux_2_28_x86_64` | ❌ 同上 |
| `ultralytics` | `py3-none-any` | ⚠️ 本身纯 Python，但**依赖 torch**（巨大且是 C 扩展） |

> `requirements.txt` 顶部写着「所有包均为纯 Python wheel，Termux 上零编译安装」。
> **引入任何真实检测库都会打破这条约束。**

**两条路，必须选一条：**

| | A. 服务端跑检测 | B. 端侧跑检测（design.md D2 已预告） |
| :--- | :--- | :--- |
| 做法 | 服务器装 onnxruntime/opencv | 手机上跑 ONNX，把算出的障碍物上报 |
| 代价 | **Termux 不能再当服务器**（得跑在正常 Linux 上），依赖树变重 | **需要一个新入口**把障碍物送进服务端做分级措辞 |
| 契约影响 | 无 | ★ 需要新路由（见表下） |

**若走 B**，服务端必须仍负责分级/措辞（那是安全关键逻辑，不能散到端上），
所以需要一个新接口，例如：

```
POST /v1/safety/grade
{ "frame": {...}, "obstacles": [ {type, position, distance_m,
                                 distance_sigma_m, confidence, ...} ] }
→ Announcement（走同一套 risk.py + phrasing.py）
```

三个选择：**新路由**（最清晰）／塞进 `Frame.extra`（省事但把 `extra` 当成了数据通道，
它本来是「上下文」）／端侧自己分级（**不要**，安全策略会分叉）。

**另一个小问题**：`read_image()` 在 `app/core/layers/perception.py:32` ——
**在 layer 模块里**。检测器要读图得反过来 import 一个 layer，层次是歪的。
建议挪到 `contracts.py` 附近或单独的 `app/core/images.py`

> **已完成（2026-09-23）**：挪到了 `app/core/images.py`，顺带加了
> `image_mime()`（按魔数判类型 —— 浏览器上传的是 JPEG、ffmpeg 抽帧是 PNG，
> 猜错 MIME 会让厂商接口回一句「图片格式不支持」这种看不出根因的 400）。
> `layers/perception.py` 保留同名再导出，旧 import 不会断。

### 1.2.1　已经有一个「VLM 当检测器」的实现（`DETECTOR=qwen_vl`）

**不是**上面 A/B 两条路里的任何一条，而是**明知违反 D2 的显式选择**，
2026-09-23 加进来，用途只有两个：联调，以及当 D2 的对照实验。

- 代码：`app/core/detectors/qwen_vl.py`；解析是纯函数 `parse_obstacles()`
  （模型会包代码块、会先说「好的，这是结果：」、会编出契约里没有的类型 ——
  逐条校验，不合规就丢）。
- **实测延迟 1.9–5.7 秒/帧**（同一台机器、真实素材）。D2 给的预算 200ms，
  中位数差一个数量级以上 —— 这就是「为什么不能一个模型全干」的量化证据。
- 距离是**问模型要的估计值**，一律带 `sigma = 0.40 × distance`（D3）。
- 失败（超时/401/429/不是 JSON）**抛异常，不返回空列表**；
  `layers/safety.py` 把它转成 `source=system` 的降级播报
  （「安全预警暂时不可用，请放慢脚步」）。
  ★ 这条与 §1.1③ 的 `Envelope` 降级**不是同一处**，也不重复：检测器这条有自己的
  措辞（「请放慢脚步」比一句通用的「系统降级了」有用得多）。而 §1.1③ 说的
  「把 `broadcast_degraded` 接到路由层」**已经做完了**（2026-09-23）。
- 默认仍是 `DETECTOR=mock`，`qwen_vl` 任何时候都不是默认值。

**A/B 那个架构问题仍然没定**：真实检测模型（YOLO 那一类）放服务端还是端侧，
取决于最终交付载体（见 §2 第 2 条）。定了之后新实现放 `detectors/` 下加个
`@register` 即可，规则层与措辞层都不用动。

#### 1.3.1 接入实测记录 —— 百度文档与实际响应有 5 处不符 ★

> 2026-09-21　｜　服务端 AK 打通后**首次真调**（太原工业学院 → 太原站，
> 12.55 公里 / 29 段）逐条核对出来的。写下来是因为：
> **照着百度文档写代码会踩这些坑，而其中第一条会让整条路线静默失效。**

**验证方法**：直接打接口看原始响应，别只读文档。

```
GET https://api.map.baidu.com/directionlite/v1/walking
    ?origin=37.957919,112.543633&destination=37.859717,112.581822
    &ak=<服务端 AK>&coord_type=wgs84&steps_info=1
```

| # | 文档 / 搜索结果说 | 实际响应是 | 不处理的后果 |
| :--- | :--- | :--- | :--- |
| 1 ★★ | 字段名 `instructions`（复数） | **`instruction`（单数）** | 只认复数 → **整条路线解析为空**，而系统会「如实降级」，看起来没报错，实际永远拿不到真实路线 |
| 2 ★ | 没提 | instruction 带 **HTML 标签**：`走30米,<b>过马路左转</b>进入<b>新兰路</b>` | 把 `<b>` 原样播给视障用户，或让 TTS 念出乱码 |
| 3 ★ | 像是有值的枚举 | **`turn_type` 可能是空字符串**（`turn_type_id` 却有值） | 转弯被判成直行 → **用户收不到那次震动提示** |
| 4 | 没提 | 距离单位**两种**：短段「走770米」、长段「走**2.1公里**」 | 播成「走2.1公里…，约 2095 米」——同一件事说两遍还换了单位 |
| 5 ★ | 没提 | 台阶的措辞是「**过阶梯**」，不是「上台阶」 | 真实路线里一段台阶被**漏报** → 用户走过台阶却收不到提示 |

**两个不在表里但同样会咬人的点：**

- **`steps_info=1` 必须传**。不传可能根本没有 `steps` 字段 —— 解析得到空列表，
  而我们会播报「未能规划到步行路线」。**把「我参数没传对」说成「没有路线」，
  是对用户说假话**，所以 `parse_walking_response()` 把「服务不可用（`None`）」
  和「确实没路线（`[]`）」分开表达。
- **`coord_type=wgs84`** 让百度做坐标系换算（端侧 GPS 原生是 WGS-84，
  百度默认收 BD-09，混用会偏几百米）。**实测有效**。
  > 附带实测：查太原站坐标时，维基百科与 BIGEMAP 差了约 **480 米** ——
  > 正是 WGS-84 与 GCJ-02 的典型偏移量。坐标系不是理论问题。

> ★★★ **最该记住的一条：静默降级会把这类错误藏起来。**
>
> 第 1 条若按文档实现，表现是「系统一直降级到内置演示路网」——
> 用户听到了一条路线，日志里没有异常，`/v1/health` 也只是平静地报 degraded。
> **不会有人发现真实地图其实从未生效过。**
>
> 所以 `routers/baidu.py` 里那行
> `_log.warning("百度路线规划返回错误: status=%s message=%s", ...)`
> 是刻意留的：对用户只能说一句「地图服务暂时不可用」，
> 但**真实原因必须留在服务端日志里**。
> （这行也是实测逼出来的：AK 类型用错时百度返回 `status=240 APP 服务被禁用`，
> 见 §1.3.2。）

**回归测试**：`tests/test_baidu_router.py` 把上表 5 条全部钉住 ——
HTML 剥离、单数/复数兼容、空 `turn_type` 回退到 instruction、
公里与米都算「自带距离」、台阶与地下通道的真实措辞。
`tests/test_route.py` 另有两条钉「距离不重复播」。

**样本文件**：`data/baidu_walking_sample.json` 是从**真实响应**截下来的
（不是照文档手写），配 `BAIDU_FIXTURE` 可在没有网络 / AK 时跑通整条链路。

#### 1.3.2 AK 的两个坑

| 坑 | 现象 | 对策 |
| :--- | :--- | :--- |
| **应用类型选错** | 用「浏览器端」AK 调 Web 服务 API → `status=240 APP 服务被禁用` | 必须新建**服务端**类型的 AK。JSAPI / JSAPI GL 属浏览器端，只用于网页显示地图 |
| **服务未勾选** | 服务端 AK 但没勾「轻量级路线规划」→ 同样 240 | 控制台 → 该 AK → 勾选「轻量级路线规划」（可能显示为「步行路线规划（轻量）」），保存后约 5 分钟生效 |

> 前后端**各一个 AK** 是标准做法：浏览器端 AK 将来给「家属端看位置」的地图界面用，
> 服务端 AK 给后端算路线用，两者不能混。

### 1.4 真实短信/推送通道 ★ 最要紧的一条　【第 1 步已完成，第 2 步仍未做】

**先说一个必须正视的问题：原来的「已通知您的家人」是空话。**

```
（改动前的原文）
app/core/rules/sos.py:42-43    "family": "已通知您的家人"
app/core/rules/fall.py:268     "已通知您的家人，请保持冷静，不要移动。"
```

全项目 `rules/` 与 `layers/` 里**没有任何发送实现**（无 SMTP、无 webhook、无推送 SDK）。
播报文本却直接断言「已通知」。对普通应用这只是没做完；**对视障安全系统，
这是在用户最危险的时刻告诉他一件没发生的事**——他会因此停止自救、原地等一个不会来的人。

> **这不是「接个通道」的事，是诚实性问题。** 两步走：
> 1. **立刻**把措辞改成不含断言的说法（如「正在通知您的家人」），直到真有通道；
> 2. 接入通道后，把**投递结果**如实反映到文本上（成功才说「已通知」）。
>
> **第 1 步已完成**：`sos.py` / `fall.py` 的文案全部改成「正在通知…」
> （`sos.py` 里那段注释写明了「接上通道、拿到真实投递结果后，才把这里改回
> 『已通知』」），`tests/test_sos.py` / `tests/test_fall.py` 各加一条回归用例
> 钉住这个不变式。**第 2 步仍待办**：没有通道，就没有投递结果可反映。

**接口改动**（接通道时）：

- 新增注册类别 `notifier`：`async def send(scope, text, location) -> DeliveryResult`；
  实现放 `app/core/providers/`（同 1.3 的扫描约束）。
- ★ **`Announcement` 可能要加字段**：投递失败时 `text` 必须不同，
  `detail.emergency` 需要能表达 `delivery: {channel, ok, error}`。
  好在这属于**只加可选字段**，符合兼容性原则。
- **家属远程查看**（`工作管理.md` §一 分工表里第四层已列）需要新路由，
  例如 `GET /v1/emergency/events/{id}` 返回事件状态 + 最后位置。
  这是个**只读查询接口**，与主流「入 `Frame` 出 `Announcement`」的形状不同。
  > 到了 2026-09-23，「非 `Frame` 入参」已经不是新事了：`POST /v1/emergency/tick`
  > （收 `{"now_ms"}`）、`GET /v1/health`、`GET /v1/frontend-config` 都不吃 `Frame`，
  > 而 `POST /v1/asr` 连出参都不是 `Announcement`（见 §零 ★④）。所以这条的
  > 决策成本比原来低 —— 照着 `/v1/asr` 那套「信封 + 原因码、失败也回 200」
  > 的规矩定形状即可，不必从零想。
